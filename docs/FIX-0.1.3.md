# 0.1.3：修复已开启授权仍不断提示的问题

日期：2026-11-02。

## 定位结果

系统 TCC 日志明确记录：

```text
Failed to match existing code requirement for subject com.framerec.app and service kTCCServiceScreenCapture
```

原构建使用 ad-hoc 签名，其 designated requirement 为单次构建的 `cdhash`。代码或资源更新后该值变化，系统设置里仍显示已开启的旧记录，但新进程不满足旧记录的代码身份要求。因此单纯重新打开或反复切换开关不能解决已有记录不匹配的问题。

## 修复

- 本机构建改为复用一个固定的本地签名证书。隐私授权要求现在由应用标识及签名证书绑定，而不是绑定单次构建的哈希。
- 私密签名材料位于应用支持目录的专用文件夹（权限 700），密码文件和加密钥匙串权限为 600。签名工具通过原生 Security API 解锁，密码不会进入命令行参数；专用钥匙串仅授权系统 `codesign` 使用私钥，签名后锁定。
- 系统信任库、默认钥匙串搜索列表和 TCC 数据库保持原配置。录屏许可由用户在 macOS 设置中授予。
- 授权尚未生效的提示增加了旧授权记录的处理步骤、当前应用路径和版本，以及在访达中显示当前应用的入口。
- 菜单顶部显示实际运行版本，方便确认已从旧进程切换到新版。

## 一次性迁移

1. 从 FrameRec 菜单完全退出旧版。
2. 在“隐私与安全性 → 录屏与系统录音”中移除旧的 FrameRec 项。
3. 用“＋”添加本次生成的 `FrameRec.app`，开启开关。
4. 打开新版，菜单应显示 0.1.3，然后再开始录屏。

新证书与原 ad-hoc 身份不同，所以本次需要用户重新绑定授权。后续构建复用相同证书，应用支持目录中的签名身份应保留。

## 验证

- `scripts/check-signing.py` 使用代码内容不同的两个程序，确认代码哈希不同，但 designated requirement 一致；新构建通过旧构建的身份要求。
- 同一个应用标识但使用其他签名的程序不能满足该要求。
- 对实际 `FrameRec.app` 的副本修改构建版本并重新签名，确认代码哈希变化而身份要求不变，新应用包通过原包的身份要求。
- 本地签名证书和私钥没有进入应用包；应用包只包含签名验证所需的公开证书。
- 23 项现有 Swift 测试通过。

实际授权记录迁移及录屏仍需要用户在系统设置中完成一次授权后验证。
